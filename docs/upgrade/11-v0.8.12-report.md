# v0.8.12 — 资产版本复核面板

## 1. 背景

`api/lifecycle.js`（review / approve / publish / revoke）在 v0.8.5 就已实现，`src/api.js`
也导出了 `apiLifecycle()`，但**没有任何组件调用它**。页面只能显示"存在待复核资产"和一串
机器可读的阻断码，无法在界面上完成批准与发布 —— 整条 extract → review → approve → publish
链路缺最后一段。

## 2. 新增

### 2.1 `src/components/ReviewPanel.jsx`（⑥ 复核与发布）

按**资产版本键**逐行展示，而不是按种类：

| 列 | 数据源 |
|---|---|
| 资产版本 | `enumerateAssetKeys` 产出的 `symbol:<pinsetId>` / `footprint:<packageId>` / `model3d:<packageId>` / `figure:<figureId>` |
| 闸门 | `bundle.assetKeyPromotion[key].promotable` |
| 状态 | `bundle.lifecycle.approvals[key]` / `.published[key]` |
| 阻断原因 | `bundle.assetKeyPromotion[key].reasons` |

三步动作条对应状态机：`① 标记已复核` → `② 批准所选` → `③ 发布所选`。理由必填并写入审计日志。

**前端不自行判断可晋升性** —— 勾选框的可用性完全取自服务端闸门结论，
`asset_not_promotable` 由服务端兜底（面板绕不过闸门，见测试）。

### 2.2 `src/promotionHelp.js`

每个 `BLOCK` 枚举值 → 中文说明 + **该去哪里处理**。独立成纯 `.js` 模块（不含 JSX），
以便被 `node --test` 直接引入做覆盖率校验：`lib/promotion.js` 每新增一个阻断码，
这里不同步补文案就会有用例失败。

### 2.3 服务端补字段

`api/generate.js` 响应新增：

- `canPublishRole` —— 此前 `canPublish` 把"无 publisher 角色"和"资产尚未批准"
  压成了同一个 `false`，面板无法给出正确提示；
- `sessionAuthenticated` —— 用于直接提示"会话未认证，任何资产都无法晋升"；
- `lifecycle` —— 面板需要 `approvals` / `published` 来显示每个资产的状态。

## 3. 实现中发现的两个约束

### 3.1 approve 之前必须先 review

状态机 `TRANSITIONS` 里 `extracted` 只允许 `edit / review / revoke`，
**`approve` 在 `extracted` 下会被拒**（`invalid_transition`）。generate 的
`markReviewed` 只影响 IR 标记，不改 `lifecycle.state`。

因此面板做成三步，并在 `canApproveNow === false` 时禁用批准按钮、给出明确提示；
`invalid_transition` 也单独做了错误文案。

### 3.2 `canPublish` 在 approve 之后就过期了

它是 generate 时算的。若直接用，批准完必须重新生成才能发布。面板改为按与服务端
相同的规则在客户端重新推导（`批准记录存在 && 闸门通过 && publisher 角色`），
使"批准 → 发布"能在同一屏内连续完成；缺 `canPublishRole` 的老响应回退到服务端值。

### 3.3 revision 回写

lifecycle 动作**必然使 revision +1**。`handleLifecycle` 把响应中的
`revision / state / lifecycle / manifest` 合入 `genResult` 并调用 `syncRevision`，
否则会复现 v0.8.11 的 409 连锁。`revision_conflict` 时面板同样自愈并提示重新生成。

## 4. 验证

```
node --test test/*.test.js
# tests 187 / pass 175 / fail 0 / skipped 12（skipped 均为缺 TEST_DATABASE_URL 的 PG 用例）

VITE_EZPLM_ORIGINS=... npm run build   # ✓
```

新增 `test/v0812.test.js` 共 9 例，全部走真实 HTTP handler：

- generate 必须提供 `assetKeyPromotion` / `canReview` / `canPublishRole` / `sessionAuthenticated` / `lifecycle`；
- 未认证会话下所有资产键均被阻断；
- **状态机：`extracted` 下直接 approve 被拒（`invalid_transition`）**；
- approve 成功 → revision +1 且 approvals 落库；
- publish 必须先 approve，且需 publisher 角色；
- 沿用过期 revision → 409 `revision_conflict` + `currentRevision`；
- 对被阻断资产 approve → 409 `asset_not_promotable`（面板绕不过闸门）；
- approve 必须携带理由；
- 每个 `BLOCK` 枚举值在面板里都有说明与处理位置。

## 5. 遗留

- `revoke` 未接入面板（撤销影响面大，建议由 ezPLM 侧发起）。
- `approximate_parametric_3d_not_vendor_step` 是结构性阻断，只要生成参数化 WRL 就必然触发；
  **model3d 在引入厂商 STEP 导入链路之前不可能晋升**，面板已明确标注这一点。
- 批准后若继续编辑，`invalidateAffectedApprovals` 会使批准失效，但面板不会主动提示"你刚
  刚作废了哪些批准" —— 需要重新生成后才看得到。
- 扫描版 PDF 的 OCR 文本行仍未接入 `analyzePage`；`＋留白` 仍为纯客户端状态。
