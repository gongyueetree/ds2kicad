# v0.8.14 — 「配好了 JWT 却仍然会话未认证」：dev 匿名身份的静默降级

## 1. 现场证据

截图里三个信息组合起来就锁定了原因：

- 状态已经是 `reviewed` → 「标记已复核」**执行成功了**，说明当前会话**有 reviewer 角色**
- 徽章「无 publisher 角色」→ 没有 publisher
- 徽章「会话未认证」→ `sessionAuthenticated === false`
- 每个资产都挂着 `no_authenticated_ezplm_session`；`symbol:default` 更是**只**挂这一条

全系统只有一种会话恰好是这个形状：

```js
// lib/auth.js
const devAnonymous = () => ({
  ok: true,
  session: { sub: 'dev-anonymous', name: '开发匿名用户', tenantId: 'dev',
             roles: ['viewer', 'editor', 'reviewer'],   // 有 reviewer，没有 publisher
             authenticated: false, devMode: true }
});
```

所以：**页面用的根本不是你配置的 JWT 会话，而是 AUTH_MODE=dev 的匿名身份。**

## 2. 根因

```js
const bearer = (req.headers?.authorization || '').startsWith('Bearer ') ? ... : null;
const token = bearer || readCookie(req, 'ezplm_session');
if (!token) {
  if (mode === 'dev') return devAnonymous();     // ← 静默降级
  return { ok: false, status: 401, ... };
}
```

而前端**刻意不携带令牌**：

```js
// src/api.js
// 鉴权令牌不得进入浏览器 bundle：浏览器直连时由同源会话/网关注入
headers: { 'Content-Type': 'application/json' },
credentials: 'same-origin'
```

这个设计本身是对的（令牌不该进 bundle），但它意味着：**只在服务端配置 `EZPLM_JWT_SECRET`
不会让浏览器自动带上令牌**。请求依旧是无令牌的 → `AUTH_MODE=dev` 把它降级为匿名 →
`authenticated: false` → 闸门恒报 `no_authenticated_ezplm_session` → 所有资产都无法晋升。

匿名身份恰好带 `reviewer`，所以「标记已复核」能点、状态能推进到 `reviewed`，
制造了"认证已经生效"的错觉；但 `publisher` 没有，`authenticated` 也是 false，
于是卡在"可批准 0 项"。

令牌必须走以下两条通道之一：

1. **同源 Cookie `ezplm_session`** —— 由 ezPLM 在同源/同父域下写入；
2. **网关注入 `Authorization: Bearer`**。

## 3. 修复

### 3.1 认证链路可诊断（`lib/auth.js` + `api/generate.js`）

会话对象新增 `authMode` / `tokenPresent` / `secretConfigured`；generate 响应新增
`authDiagnostics`（不含任何密钥内容）：

```json
{ "authMode": "dev", "secretConfigured": true, "tokenPresent": false,
  "devMode": true, "roles": ["viewer","editor","reviewer"],
  "sessionTenantId": "dev", "jobTenantId": "dev" }
```

此前 dev 降级是**完全静默**的 —— 运维配好了密钥，页面却只说"会话未认证"，说不出为什么。

### 3.2 复核面板显式告警（`ReviewPanel.jsx`）

`devMode === true` 时在面板顶部直接给出橙色告警块：说明这是匿名身份而非配置的 JWT 会话、
本次请求是否携带令牌、为什么「标记已复核」能点但批准不了、令牌该走哪条通道、
以及生产环境应设 `AUTH_MODE=production`。诊断区同时列出 AUTH_MODE / 密钥是否配置 /
是否携带令牌 / 角色 / 会话租户 / 作业租户。

**租户提示**：会话租户与作业租户不一致时明确提示——换成真实 JWT 后访问旧作业会得到
403 `tenant_mismatch`，**必须重新提取一次**生成属于新租户的作业。这是最容易踩的后续坑：
之前用匿名身份（`tenantId=dev`）提取的所有作业，认证之后一个都打不开。

### 3.3 `scripts/mint-session.mjs`

本地/联调签发会话 JWT，输出令牌本身 + 浏览器控制台设置 Cookie 的命令 + curl 示例。
它要求调用者已掌握 `EZPLM_JWT_SECRET`，等同于 ezPLM 正常签发会话，**不构成权限提升**
（刻意没有做成 HTTP 接口——那才会是真正的提权面）。

```
EZPLM_JWT_SECRET=xxx npm run mint-session -- \
  --sub u1 --tenant eetree --roles reviewer,publisher \
  --iss https://ezplm.cn --aud ds2kicad --origin https://ds2kicad.example.com
```

```
node --test test/*.test.js

VITE_EZPLM_ORIGINS=... npm run build   # ✓
```

`test/v0812.test.js` 新增 4 例：

- **复现现场**：全程不带令牌 + `AUTH_MODE=dev` → 200 但 `sessionAuthenticated:false`、
  `canReview:true`、`canPublishRole:false`、`authDiagnostics.tokenPresent:false`，
  且每个资产都含 `no_authenticated_ezplm_session`；
- `AUTH_MODE=production` 下无令牌直接 401，不再静默降级；
- **Cookie 通道**：`ezplm_session` 与 Bearer 等效，产生 `authenticated:true` 会话；
- **租户隔离**：匿名身份创建的作业，换成真实 JWT 后 403 `tenant_mismatch`。

## 5. 部署清单

| 项 | 值 |
|---|---|
| `EZPLM_JWT_SECRET` | 与 ezPLM 签发端一致 |
| `EZPLM_JWT_ISS` / `EZPLM_JWT_AUD` | 与 JWT 的 `iss` / `aud` 完全一致 |
| `AUTH_MODE` | **`production`**（dev 会静默降级，掩盖配置问题） |
| Cookie | ezPLM 写入 `ezplm_session`；跨站 iframe 需 `SameSite=None; Secure` |
| JWT 载荷 | `sub` / `tenantId` / `roles:["reviewer","publisher"]` / `iss` / `aud` / `exp` |

改完之后 `symbol:default` 会立刻变为"通过"（它唯一的阻断就是认证）。
`figures` 还需要在 ④ 确认图区（当前 0/4）；`footprint` 需要补齐 ③ 的机械尺寸与证据；
`model3d` 仍受结构性阻断限制。
