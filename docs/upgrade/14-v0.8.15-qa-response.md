## 1. 已修复

### DSK-010 CNY17F 400 mil 封装与 3D 引脚行距错误（生产阻断）

**根因**（`lib/validate.js:243`）：

```js
rowSpan: field('rowSpan', 7.62, 2.54, 30),   // 无条件默认 300 mil
```

DIP 的孔距**从不使用**已提取的 `leadSpan`（现场值 10.16），也**不读封装名里的 `400 mil`**。
AI 没给 `rowSpan` → 落到默认 7.62 → 焊盘、KLC 文件名后缀、WRL 引脚三处一致地错成 300 mil。

**修复**：

1. 新增按可信度排序的孔距解析：
   `手册 land pattern > 显式 rowSpan > 封装名标称（400 mil → 10.16）> leadSpan > 默认值`；
2. **名称矛盾检查**：封装名标称与几何相差 > 0.3 mm 时以名称为准（"400 mil 却 7.62 mm"
   是物理矛盾），并写入 `fieldProvenance.rowSpan.source = 'corrected'` 留痕；
3. 标准孔距吸附（7.62 / 10.16 / 15.24 / 22.86），手册写 10.2 也能落到 400 mil；
4. **单一真值源**：`dipPads` 此前用 `lp?.rowSpan || pkg.rowSpan`，而文件名后缀与 3D 都取
   `pkg.rowSpan`，两者不一致时就会生成"名字写 400 mil、焊盘却是 300 mil"的封装。
   现在 land pattern 的孔距在 `sanitizePackage` 阶段就折算进 `pkg.rowSpan`，下游只认它。

采纳了报告的建议「封装回归必须断言焊盘坐标而不只断言焊盘数量」：新用例直接从
`.kicad_mod` 正则提取每个焊盘的 X 坐标算行距、从 WRL 提取 translation 算引脚中心距，
并断言 KLC 文件名后缀与几何同源。

### DSK-001 AP2112 生成阶段 422「文件哈希不一致」

**根因**：`symbolVariantName` 只对**第一个**分组特殊处理：

```js
if (isFirst) return mpn;                       // AP2112
return `${mpn}_${tag}`;                        // tag 来自 tiCode/type/name
```

AP2112 有 4 个 pinset、封装类型同为 SOT-25 → g1=`AP2112`，g2/g3/g4 **全叫 `AP2112_SOT25`**。
于是 `assembleAssets` 把三份不同内容写进同一个 `AP2112_SOT.lib` 路径，
`verifyConsistency` 逐文件比对时必然对不上，报出那句语焉不详的「文件哈希不一致」。

（注：两个分组是撞不出来的，必须 3 个以上同类型 pinset 才复现——回归用例据此构造。）

**修复**：符号名唯一化（撞名追加 `_2`/`_3`）；并在 `assembleAssets.push()` 就地拦截同路径
不同内容，抛出 `资产路径冲突：X.lib 被写入两份不同内容`，把它变成可定位的诊断而不是
下游的哈希谜题。

### DSK-002 旧版 `.lib` 不是完整库

新增 `wrapLegacyLibrary()`：补 `EESchema-LIBRARY Version 2.4` + `#encoding utf-8` 库头与
`#End Library` 库尾。在线 Viewer 只解析 `DRAW…ENDDRAW` 区段，不受影响（已在用例中断言）。

选择"补齐"而非"取消下载项"，是因为旧版格式对仍在用 KiCad 5 的用户有价值，且成本极低。

### DSK-012 SHT3x-DIS 激光标记图被误分类

标题 `Top view of the SHT3x-DIS illustrating the laser marking` 命中了 `pin_configuration`
白名单里的 `top view`。新增 `reclassifyByTitle()`，在过滤前做确定性重分类，
标记/丝印类（`laser marking` / `marking information` / `激光标记` / `丝印`）优先于 `top view`
判定，归入 `package_outline`，并记录 `kindReclassified` 供审计。同时纠正另两类错分。

## 2. 部分处理（有意保守）

### DSK-005 / DSK-006 管脚名语义

新增 `lib/pinlint.js`。**只自动修正在字面上不可能有歧义的一类**：字母 `O` 被 OCR 成
数字 `0`，且修正后是标准信号名前缀（`GPI0`→`GPIO`、`V0UT`→`VOUT` 等 15 条）。
`VDD0` / `P0` / `IO0` / `CH0` 等合法名有专门的反例用例保护。

其余**一律只标记不改写**：

| 规则 | 为什么不自动改 |
|---|---|
| `duplicate_pin_name` | 两个 `SUSPEND` 里哪一个该带低有效标记，字面上无从判断 |
| `possible_footnote_in_pin_name` | `NC1/Vpp2` 的 1 和 2 是脚注还是编号，字面上无从判断 |
| `exposed_pad_name_unverified` | `EPAD` 是否应为 `GND` 取决于手册，不能猜 |

每条命中都写进 `transformationLog` 并置 `reviewRequired`，晋升闸门据此阻断。
猜错比不猜更危险——这与项目"证据绑定、AI 管语义、确定性引擎管几何"的原则一致。

### DSK-003 封装生成覆盖不足

**未做**家族扩展（Module / LGA / TSSOP / DHVQFN / SMD-6）——那是四个独立的几何引擎，
不适合和缺陷修复混在一个补丁里。

**已做**报告建议的另一半："候选列表应在生成前明确显示支持/不支持"。此前
`familySupported` 在服务端算得好好的，**前端一次都没读过**，用户勾选、生成、然后才发现
没有封装。现在候选下拉直接标 `⚠ 不支持生成封装`，选中时给出橙色说明块（含判定依据与
改判入口），勾选框文案也随之变化。

### DSK-008 URL 输入

「清空后回弹默认 TI URL」**没能复现**：`url` 只有三处写入（初始值、ezPLM postMessage、
`onChange`），标准受控输入清空后应保持空值。报告自己也标注为自动化兼容性观察。

但顺着看发现了更实在的缺陷：URL 为空时 `if (!u) return;` **静默返回，页面毫无反馈**。
已补必填校验与 `http(s)://` 格式校验。

## 3.5 v0.8.16 追加修复

### DSK-011 符号侧点击命中相邻管脚

**根因**（`src/viewer/symbolRender.js`）：透明命中区的宽度写成 `40 / scale`，
即恒为 **40 屏幕像素**；而相邻管脚在用户坐标里固定相隔 100 单位（`MIL = 100`）。
符号越密 `scale` 越小，`40 / scale` 就越可能超过 100 —— 相邻命中区互相重叠，
**后绘制的管脚盖住先绘制的**，于是点 1 命中 3、点 4 命中 6、点 25 命中 24。
封装侧没有这个问题，因为焊盘是各自独立的图元，这与报告"封装侧 5/5 正确、符号侧 7 中 2"
的观测完全吻合。

**修复**：把命中宽度钳制在管脚间距的 72% 以内（`Math.min(40 / scale, PIN_PITCH * 0.72)`），
并显式声明 `pointer-events: stroke` 与 `stroke-linecap: butt`，杜绝端点外溢。

### DSK-013 同一 PDF 的图区候选数量不稳定

**根因**（`api/extract.js:306`）：

```js
need.figures ? sanitizeFigures(raw?.figures) : sanitizeFigures(det.figures)
```

解析器与 AI 是**二选一**：解析器有结果就完全不要 AI 的，没有才用 AI 的。
于是同一份 CNY17F PDF 因模型波动，一次得到 2 张、一次得到 0 张。

**修复**：新增 `mergeFigureCandidates()`，改为**始终合并**：

- 解析器结果确定性、可复现 → 永远保留；
- AI 结果只**补充**解析器没找到的图；
- 去重键为 `页码 + 类型`，同页同类型以解析器为准；
- 输出按 `(页码, 类型, 标题)` 稳定排序，消除上游数组顺序带来的抖动；
- 每张图带 `candidateSource`（`parser` / `gemini`），来源可追溯。

数据来源标记同步改为 `parser+gemini`，不再谎称单一来源。

**残留**：AI 补充的那部分仍会波动——这是模型固有的。但**确定性部分从此稳定**，
且用户能从 `candidateSource` 看出哪些图是可复现的。彻底消除波动需要 DSK-004 的
幂等作业改造。
