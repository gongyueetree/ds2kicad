# v0.8.11 — 版本冲突（乐观锁失步）与"按钮无反应"修复

## 1. 现象

1. 页面顶部报 `✕ 版本冲突：当前 revision 2`；
2. 点击最下方「✓ 确认无误，生成 N 个封装的 KiCad 符号 / 封装 / 3D」**毫无反应**。

## 2. 根因

### 2.1 `figure-upload` 会递增 revision，而页面丢弃了返回值

`api/figure-upload.js` 每次上传都执行一次真实提交：

```js
const commit = await store.commitGeneration(jobId, { ir: nextIr, expectedRevision: job.revision, ... });
return res.status(200).json({ ..., revision: commit.job.revision });   // ← 新版本号
```

而 ④ 编辑器的「确认此图（截取并上传）」把响应整个丢掉了：

```js
await apiFigureUpload({ ..., expectedRevision: revision });   // 返回值未接收
setStatus('图片已上传到服务端 ✓');
```

于是 `extract.revision` 永久停留在上传前的值。后果是**从第一次「确认此图」开始，
之后所有写操作全部 409**：

- 确认第二张图 → `版本冲突：当前 2`
- 点击生成 → `expectedRevision` 仍是旧值 → 409

这也解释了为什么截图里 revision 已经是 2 —— 用户已经成功上传过一张图。

### 2.2 错误码在客户端 API 层被丢掉

```js
// src/api.js（旧）
throw new Error(data.error || `${path} 返回 ${r.status}`);
```

服务端返回的 `code: 'revision_conflict'` 与 `currentRevision` 全部丢失，客户端拿到的只有一句
人类可读的文案，**无法据此自愈**。

### 2.3 生成失败的错误渲染在页面顶部，用户看不到

`doGenerate` 的 `catch` 里 `setError(e.message)`，但 `error` 只在**页面最顶部的 URL 卡片**里渲染
（`{error && <p className="error-line">✕ {error}</p>}`）。生成按钮在页面最底部，两者相距整屏。
用户点击 → 请求发出 → 409 → 错误写到屏幕外 → **表现为"按钮没反应"**。

`phase` 也被复位回 `'confirm'`，按钮文案瞬间恢复原样，进一步强化了"什么都没发生"的错觉。

## 3. 修复

### 3.1 根治：上传后回写版本号

```js
const r = await apiFigureUpload({ ... });
onRevision?.(r.revision);
setStatus(`图片已上传到服务端 ✓（revision → ${r.revision}）`);
```

`App` 通过 `syncRevision(rev)` 更新 `extract.revision`。上传失败时同时把 `confirmed` 复位为
`false`，避免留下"已确认但服务端没有图"的假象。

### 3.2 错误码穿透

`src/api.js` 新增 `apiError()`，把 `status` / `code` / `currentRevision` / 原始 `payload`
挂到 `Error` 对象上，`apiLoadJob` 同样改用它。

### 3.3 乐观锁自愈

- **上传遇 409**：直接用 `e.currentRevision` 同步，提示用户再点一次。
- **生成遇 409**：调用此前**已导入却从未使用**的 `apiLoadJob`，从服务端拉回权威 IR
  （part / packages / pinsets / figures / revision / `__original`）重新对齐，然后提示
  「页面已同步到最新内容，请核对后再次点击生成」。

  这里**刻意不自动重试**：409 也可能来自他人的并发改动，盲目重试会覆盖对方的修改。
  拉回后由人确认再提交，符合本项目"全部结果经人工确认"的前提。
  重新对齐时按 `figureId` 保留客户端的 `fitMethod / fitCaption / aiBbox`，不丢失几何溯源。

### 3.4 错误就地可见

生成按钮所在的 `.generate-card` 内就地再渲染一份错误行。顶部那份保留（提取阶段的错误仍在那里）。

## 4. 验证

```
node --test test/*.test.js
# tests 178 / pass 166 / fail 0 / skipped 12（skipped 均为缺 TEST_DATABASE_URL 的 PG 用例）

VITE_EZPLM_ORIGINS=... npm run build   # ✓
```

新增 `test/v0811.test.js` 共 4 例，走真实 HTTP handler：

- `figure-upload` 成功后 revision 递增，且响应必须返回新版本号；
- **复现缺陷**：沿用上传前的 revision 再次上传 → 409 `revision_conflict` + `currentRevision`；
  同一 revision 提交 generate 同样 409（即"按钮没反应"的服务端真相）；
- 修复后行为：逐次回写响应中的 revision，连续上传三张图后 generate 成功；
- `src/api.js` 的 409 必须把 `code` / `currentRevision` 挂到 `Error` 上（此前只剩 message）。

## 5. 遗留

- `apiLifecycle` 也会递增 revision，目前前端尚无调用点；接入发布流程时必须同样回写。
- 并发场景下的差异合并（谁改了哪些字段）尚未实现，当前策略是整体拉回 + 人工复核。
- `＋留白` 仍为纯客户端状态，不写回 IR；扫描版 PDF 的 OCR 文本行仍未接入 `analyzePage`。
