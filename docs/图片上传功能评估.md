# 「上传图片生成资产」功能评估

**结论：技术上可做，且改动量比想象中小；但有一个必须先决策的问题 —— 证据链。**

---

## 1. 技术可行性：管线已经通了大半

`lib/gemini.js` 现在是这样送文档的：

```js
{ inline_data: { mime_type: 'application/pdf', data: pdfBase64 } }
```

Gemini 的多模态接口对 `image/png`、`image/jpeg` 一视同仁，**换个 mime_type 就能收图**。
下游 `sanitizePackage` → `normalizeGeometryDetailed` → `generateBundle` 全是纯函数，
不关心输入是 PDF 还是图片。

真正要改的只有四处：

| 位置 | 改动 |
|---|---|
| `api/extract.js` | 接受 image mime；跳过 `slicePdf` / `selectRelevantPages` / `pdftext` 整条 PDF 预处理链 |
| `lib/gemini.js` | 按输入类型切换 `inline_data`；提示词改为"单图"版本 |
| `src/pdf.js` / 图集 | 图片没有"页"的概念，`page` 恒为 1，`bbox` 即整图；`analyzePage` 需绕过 pdf.js |
| 证据锚点 | `SOURCE_TYPE` 需新增 `user_uploaded_image`（见第 3 节） |

**工作量估计：核心链路 1～2 轮，图集与证据体系另计。**

---

## 2. 但 v0.8.18 这个缺陷正好说明了风险所在

刚修的 DSK-015 是：AI 把 SOT23-5 的本体长读成 4.9mm（实际 2.9mm），
两道几何守卫因容差过松没拦住，符号/封装/3D 全部按错值生成。

**这个缺陷在图片输入下会更频繁，因为兜底信息更少：**

| 兜底手段 | PDF 输入 | 单张图片输入 |
|---|---|---|
| 文本层交叉校验（`pdftext`） | 有 | **无**（截图通常无文本层） |
| 多页互证（管脚表 vs 机械图 vs 框图） | 有 | **无** |
| 封装名/型号解析（如 `400 mil` → 10.16mm） | 有 | 取决于图里有没有印 |
| JEDEC 先验 | 有 | 有（唯一完整保留的） |
| 关系校验（引脚数 × pitch） | 有 | 有 |

也就是说，**图片输入下几乎只剩 JEDEC 先验 + 关系校验两道防线** ——
而这两道正是刚刚被证明会漏的那两道。

## 3. 必须先决策的问题：证据链怎么算

项目有一条贯穿始终的硬规则：**每个值必须可追溯到来源**
（`EvidenceAnchor` 记录 `documentSha256` / `page` / `bbox`）。
晋升闸门是 fail-closed 的 —— 缺锚点直接判阻断，删掉证据不会放行。

用户上传的截图：

- 没有 `documentSha256` 可绑（那是数据手册的哈希，不是截图的）
- 没有 `page`
- 无法验证这张图**真的来自它声称的那份手册**

有三条路：

### 方案 A：图片资产恒不可晋升（推荐）

新增 `SOURCE_TYPE.USER_UPLOADED_IMAGE` 与阻断码
`source_is_user_image_not_datasheet`，性质等同于现有的
`approximate_parametric_3d_not_vendor_step` —— **结构性阻断，补数据也清不掉**。

- 图片通道产出的资产可以下载、可以在 KiCad 里用，但**永远进不了 ezPLM 正式库**
- 定位为"快速草稿 / 应急"，与正式流程物理隔离
- UI 上需要有明显的通道标识（类似 mock 数据的条纹徽章）

**优点**：不破坏现有证据体系，实现最简单，风险可控。
**代价**：图片通道的产出无法走完整流程，用户可能觉得"做了一半"。

### 方案 B：图片 + 手册 URL 双输入

用户上传截图的同时必须提供来源手册 URL，服务端仍下载 PDF 算哈希，
截图作为"人工指定的关键区域"辅助 AI 定位。

**优点**：证据链完整，可以正常晋升。
**代价**：没有解决"手里只有一张图"的原始诉求 —— 那种情况本来就没有手册。

### 方案 C：图片本身作为证据源

把上传图片存入 objectstore，用它自己的 sha256 作锚点，
`sourceType` 标为 `user_uploaded_image`，允许晋升但在 manifest 里如实记录来源等级。

**优点**：最灵活。
**代价**：**把"证据"的定义从"厂商手册"松绑到"用户提供的任意图片"**。
一旦开这个口子，闸门的意义会被显著削弱 —— 任何人截个图就能让资产通过。
不建议在没有额外审批层的情况下这么做。

---

## 4. 建议

**先做方案 A 的最小版本**，理由：

1. 它不触碰证据体系与晋升闸门，不会引入 v0.8.18 那类"守卫失效"的连带风险；
2. 能立刻验证"图片输入的提取质量到底如何" —— 这是决定后续投入的关键数据；
3. 如果实测发现图片输入的几何错误率高到不可用，那方案 B/C 也就不必讨论了。

**配套建议：图片通道应强制走人工确认。** 具体说，图片输入下：

- 所有几何字段的 `fieldProvenance.source` 标为 `user_image_inference`
- 默认全部进入 ③ 封装页的待确认状态（红色标注）
- 生成前必须逐项确认，而不是像 PDF 通道那样"有值就先生成"

**另外，v0.8.18 的遗留项在这里变得更重要：**
先验表目前只覆盖 7 类小信号封装（SC70 / SOT23 / MSOP / TSSOP / SSOP / SOIC）。
图片通道既然主要靠先验兜底，**扩充先验表应作为图片功能的前置工作**，
至少补齐 QFN / DFN / SOT-89 / SOT-223 / DPAK 等常见类型。

---

## 5. 一个更省事的替代方案

如果核心诉求只是"手里有一张封装图，想快速出资产"，
可以先做一个**成本低得多的中间态**：现有的 ④ 图区截取已经能从 PDF 裁图，
把它反过来用 —— 允许用户**上传图片替换某一张已识别的图区**，
但尺寸仍从 PDF 提取。这样证据链不断，实现只需扩展 `figure-upload` 接口。

这条路解决不了"完全没有手册"的场景，但如果实际使用中大多数情况是
"手册有、只是某张图 AI 没识别好"，那它的性价比高得多。

**需要你判断的是：真实场景里"完全没有 PDF、只有一张图"占多大比例？**
这个比例决定了该走方案 A 还是这个替代方案。
