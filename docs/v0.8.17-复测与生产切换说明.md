# 第一部分：复测指南

## 0. 开始之前必须知道的两件事

**（1）本轮站点仍处于 `AUTH_MODE=dev`，这是有意的。**

页面上每个资产都会显示 `no_authenticated_ezplm_session`，「⑥ 复核与发布」里
可批准项恒为 0。**这不是缺陷**——浏览器直连时不携带 ezPLM 会话令牌，服务端按
fail-closed 原则降级为匿名身份。认证链路的切换安排在几何验证通过之后（第二部分），
本轮请**沿用上一轮的范围口径**：发布权限与晋升不在测试范围内。

复核面板顶部会有一块橙色告警明确说明当前是匿名身份，展开「会话与权限诊断」
可以看到 `authMode / tokenPresent / devMode` 的实际取值。如果它显示的和这里说的不一致，
那反而是需要报告的问题。

**（2）v0.8.17 修改了几何生成逻辑，回归重点在几何而非流程。**

上一轮报告里 13 条缺陷，本轮处理了 10 条，另新增修复 1 条（DSK-014，报告未发现）。
请优先复测下表中标 **P1** 的项。

## 1. 复测清单

### DSK-010（P1，上一轮的生产阻断项）DIP 孔距

**改了什么：** `rowSpan` 此前无条件默认 7.62mm（300 mil），DIP 既不使用已提取的
`leadSpan`，也不读封装名里的 `400 mil`。现改为按可信度解析：
`手册 land pattern > 显式 rowSpan > 封装名标称 > leadSpan > 默认值`，
并在封装名标称与几何相差 > 0.3mm 时以名称为准（"400 mil 却 7.62mm"属物理矛盾）。

**必测用例：**

| 用例 | 输入 | 通过标准 |
|---|---|---|
| 原缺陷复现 | Vishay CNY17F → `DIP-6 (400 mil)` | `.kicad_mod` 两列焊盘中心距 = **10.16mm**；WRL 两排引脚中心距 = **10.16mm**；文件名后缀为 `W10.16mm` |
| 防误伤 | 任一普通 300 mil DIP（如 PDIP-8） | 孔距仍为 **7.62mm**，未被名称解析误改 |
| 扩展 | 一个 600 mil DIP（如 PDIP-40） | 孔距 = **15.24mm** |
| 扩展 | 带手册推荐 land pattern 的 DIP | land pattern 孔距、`pkg.rowSpan`、文件名后缀、WRL 四者一致 |

**审核方法**（沿用上一轮的坐标断言，不要只数焊盘个数）：
读 `.kicad_mod` 中 1/2/3 与 6/5/4 两列焊盘的 X 坐标算差值；
读 WRL 的 `translation` 第一个分量，按 `1 unit = 2.54mm` 换算。

**关注点：** 文件名、焊盘坐标、WRL 引脚三者现在共用同一个 `pkg.rowSpan` 真值源。
若发现任意两者不一致，说明单一真值源的收敛还有漏网路径，请立即报告。

### DSK-014（P1，新修复，上一轮未发现）QFN 3D 端子被本体吞没

**现象：** TMUXL27518（WQFN-24, 4×4mm）3D 预览中四条边的引脚看起来"连成一片"。

**根因不是横向间距**——端子宽 0.25mm、间距 0.5mm、缝隙 0.25mm，横向完全正确。
问题在 Y 轴：端子占 `0~0.2mm`，本体从 `standoff=0.02mm` 起，**端子 90% 埋在环氧内部**，
每个只剩 0.04mm 边缘可见；EP 整块被吞没、完全不可见。

**改了什么：** 端子层 `0~termH`、本体 `termH~height`，两者不再重叠；
`端子层 + 本体 = 手册标称总高`；EP 移到与端子同层。仅影响 `qfn` 家族。

**必测用例：**

| 用例 | 通过标准 |
|---|---|
| TMUXL27518 WQFN-24 | 3D 中四条边各能**数出 6 个独立端子**，之间有可见缝隙 |
| 同上 | 本体下方能看到 **2.45×2.45 的 EP 方块** |
| 同上 | 无 z-fighting（表面闪烁/斑驳） |
| 同上 | 模型总高仍为 **0.8mm**（手册标称），未溢出 |
| 防误伤 | 任一 SOIC / TSSOP / DIP | 3D 引脚形态与上一轮一致，未变化 |

**给审核脚本的建议：** 上一轮 5.5 节验的是「节点数量、拓扑分类、平面尺寸」——
这三项本来就是对的（24 个端子确实都生成了、位置也对），所以没抓到这个缺陷。
**缺的是遮挡/互穿检查**。建议在 `audit_graphics_3d.py` 里增加两条断言：

1. 任意两个不同材质的实体不得竖直互穿（引脚顶面 ≤ 本体底面）；
2. 每个引脚节点必须至少有一个方向探出本体包围盒。

### DSK-001（P0）AP2112 生成阶段 422 哈希不一致

**根因：** `symbolVariantName` 只对第一个分组特殊处理，AP2112 的 4 个 pinset 封装
类型同为 SOT-25 → 第 2/3/4 个符号变体**全叫 `AP2112_SOT25`**，三份不同内容写进同一个
`.lib` 路径。注意：**两个分组撞不出来，必须 ≥3 个同类型 pinset 才复现。**

**必测：** AP2112 提取 → 包含全部候选封装生成。

**通过标准：** HTTP 200；符号变体名两两不同；`.lib` 文件路径无重复；manifest 哈希一致。
若仍失败，错误信息现在会是 `资产路径冲突：X.lib 被写入两份不同内容`（可定位），
而不是原来那句语焉不详的「文件哈希不一致」。

**建议扩展：** 再找一个 ≥3 pinset 的器件验证泛化性。

### DSK-011（P2）符号侧点击命中相邻管脚

**根因：** 命中区宽度写成 `40 / scale`，即恒为 40 **屏幕像素**；而相邻管脚在用户坐标里
固定隔 100 单位。符号越密 `scale` 越小，`40/scale` 越可能超过 100 → 相邻命中区重叠，
后绘制的盖住先绘制的。封装侧没这问题（焊盘是独立图元），与上一轮"封装侧 5/5 正确、
符号侧 7 中 2"的观测吻合。

**必测：** TMUXL27518 在线预览，符号侧依次点击 1/2/3/4/5/6/25。
**通过标准：7/7 命中自身编号**，两侧仅高亮该编号。建议对**管脚最密的器件**（如 CP2102/9 的 QFN28）
额外抽查——scale 越小越容易暴露。

# 第二部分：生产切换说明

## 4. 一个关键事实：大部分环境变量早已生效

`IS_PROD` 的判定是：

```js
process.env.NODE_ENV === 'production' || process.env.VERCEL_ENV === 'production' || !!process.env.VERCEL
```

**Vercel 在 Preview 环境也会设 `VERCEL=1`**，所以以下变量在当前站点上**已经是硬性必填**
（缺任何一个都会 fail-closed，站点跑不起来）：

| 变量 | 缺失后果 |
|---|---|
| `DATABASE_URL` | 抛错：Serverless 多实例下 SQLite 不共享，作业会丢失 |
| `PDF_TOKEN_SECRET` | 抛错：PDF 取回令牌不可复现 |
| `ASSET_TOKEN_SECRET`（或复用 `PDF_TOKEN_SECRET`） | 抛错 |
| `EZPLM_JWT_ISS` / `EZPLM_JWT_AUD` | 所有请求鉴权失败 |
| `EZPLM_JWT_SECRET` | 503 拒绝未鉴权访问 |
| `VITE_EZPLM_ORIGINS` | **构建期**失败（有意的 fail-closed，防止 postMessage 白名单为空就上线） |
| `GEMINI_API_KEY` | `/api/extract` 返回 503 |

**结论：切生产不需要补配这些，它们已经配好了。**

## 5. 切换动作：只改一个变量

当前 `AUTH_MODE=dev`。它让**无令牌请求**被静默降级为匿名身份
（`sub=dev-anonymous`，`roles=[viewer,editor,reviewer]`，`authenticated=false`）——
这正是所有资产恒挂 `no_authenticated_ezplm_session` 的原因，也正是「标记已复核」
能点（匿名恰好带 reviewer）但批准不了（无 publisher、未认证）的原因。

**切换步骤：**

1. Vercel → Project Settings → Environment Variables
2. 将 `AUTH_MODE` 由 `dev` 改为 `production`（或**直接删除**该变量——
   Vercel 上 `NODE_ENV=production`，默认值本就是 `production`）
3. **Deployments → 最新一次 → Redeploy**

> **环境变量改动必须手动 Redeploy 才生效**，等自动部署没用。这是已知踩过的坑。

切换后行为：无令牌请求直接 **401**，不再静默降级。配置问题会立刻暴露而不是被掩盖。

## 6. ezPLM 侧需要配合的事

前端 `src/api.js` **刻意不把令牌写进浏览器 bundle**：

```js
headers: { 'Content-Type': 'application/json' },
credentials: 'same-origin'
```

令牌必须走以下两条通道之一，**只在服务端配 `EZPLM_JWT_SECRET` 不会让浏览器自动带上令牌**：

1. **同源 Cookie `ezplm_session`**（前端依赖的正是这条）
2. **网关注入 `Authorization: Bearer`**

### JWT 载荷要求

```json
{
  "sub": "<用户 ID>",
  "name": "<显示名>",
  "tenantId": "<租户 ID，必须与作业所属租户一致>",
  "roles": ["reviewer", "publisher"],
  "iss": "<必须等于 EZPLM_JWT_ISS>",
  "aud": "<必须等于 EZPLM_JWT_AUD>",
  "exp": 1234567890
}
```

- `roles` 也接受 `role` 或 `scope`；角色隐含关系：`publisher ⊃ reviewer ⊃ editor ⊃ viewer`
- 缺 `roles` → 默认最小权限 `viewer` → 复核/批准全部 403 `insufficient_role`
- **`sessionAuthenticated: true` 只说明验签通过，与角色是两回事**
- `tenantId` 与作业不符 → 403 `tenant_mismatch`

### Cookie 属性

- 同域/同父域部署：`HttpOnly; Secure; SameSite=Lax; Path=/`
- **跨站 iframe 嵌入 ezPLM**：必须 `SameSite=None; Secure`，否则浏览器不会发送。
  第三方 Cookie 限制尚未实测，若受阻请改用网关注入 Bearer。

## 7. ⚠ 切换后必须重新提取：旧作业会全部失效

**这是最容易踩的坑。** 作业创建时会绑定 `tenantId = session.tenantId`。
当前所有作业都是匿名身份创建的，`tenantId = "dev"`。切换到真实 JWT（如 `tenantId=eetree`）后：

```
GET/POST 任何旧 jobId → 403 tenant_mismatch
```

**切换前请确认没有需要保留的在途作业，切换后所有器件必须重新提取。**

## 8. 切换后的验收步骤

1. 从 ezPLM 携带令牌进入，或用仓库自带脚本本地签发验证：

   ```
   EZPLM_JWT_SECRET=<与服务端一致> npm run mint-session -- \
     --sub u1 --tenant <租户ID> --roles reviewer,publisher \
     --iss <EZPLM_JWT_ISS> --aud <EZPLM_JWT_AUD> --origin https://ds2kicad.vercel.app
   ```

   脚本会输出可直接粘贴的 `document.cookie = ...` 命令。
   它要求调用者已掌握 `EZPLM_JWT_SECRET`，等同 ezPLM 正常签发，不构成权限提升
   （**刻意没做成 HTTP 接口**——那才是真正的提权面）。

2. 重新提取一个器件 → 生成 → 展开「⑥ 复核与发布 → 会话与权限诊断」，逐项核对：

   | 字段 | 期望值 |
   |---|---|
   | `authMode` | `production` |
   | `tokenPresent` | `true` |
   | `devMode` | `false` |
   | `canReview` | `true` |
   | `canPublishRole` | `true`（若签发了 publisher） |
   | 会话租户 / 作业租户 | 两者一致 |

3. **`symbol:default` 应立刻变为「通过」**——它唯一的阻断就是认证。这是最快的验证信号。

4. 走通三步状态机：`① 标记已复核 → ② 批准所选 → ③ 发布所选`。
   注意状态机要求 **approve 之前必须先 review**（`extracted` 下直接 approve 会被拒
   `invalid_transition`）。

## 9. 认证打通后仍会存在的阻断（属预期）

| 资产 | 剩余阻断 | 如何清除 |
|---|---|---|
| `symbol` | 无 | 认证后即可晋升 |
| `figure:*` | `no_confirmed_figures` | 在 ④ 确认图区**并重新生成**（闸门读的是 IR 里的 `confirmed`，页面点了不提交不算） |
| `footprint:*` | `missing_required_geometry`、`package_field_evidence_unverified`、`field_evidence_default_value`、`land_pattern_derived_not_from_datasheet` | 在 ③ 对照机械图逐项补齐并确认。**注意删除 evidence 不会放行，缺锚点直接判阻断**（fail-closed） |
| `model3d:*` | `approximate_parametric_3d_not_vendor_step` | **无法清除。** 结构性阻断，需引入厂商 STEP，链路未实现 |

## 10. 回滚

切换后若出现大面积 401，把 `AUTH_MODE` 改回 `dev` 并 **Redeploy** 即可恢复。
代价是所有资产重新变为不可晋升——但功能测试可继续。
